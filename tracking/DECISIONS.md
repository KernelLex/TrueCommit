### 2026-08-27 — packet P15: real contact identity (name + phone), and the judgment calls inside it
**What:** every debtor/customer in this codebase shared exactly one synthetic fake contact (`DEMO_CUSTOMER_CONTACT = "+919812345678"`, `DEMO_CUSTOMER_EMAIL`) since Day 6, used everywhere a real Razorpay customer object or a dispatched voice/SMS/message record needed a "who". P15 (user-confirmed new scope, same "new feature, freeze/cut-order restated" pattern as P13/P14) lets an operator submit a REAL name + phone for a debtor via `POST /entities/{id}/contact`, and wires exactly one function — `WorldRunner.resolve_contact()` — as the single place every dispatch point (autonomous voice/message escalation, manual voice/SMS/message reminders, and the real Razorpay payment-link/mandate calls) reads WHO to contact.

**No real call/SMS/WhatsApp message is placed, by design, and this is unchanged by the packet.** There is no telephony/SMS-gateway/WhatsApp-Business credential anywhere in this project. A submitted contact only ever affects (a) what the audit trail and dashboard display from then on, and (b) the `customer.contact` field sent to the REAL Razorpay TEST API when `PK_REAL_RAZORPAY=1` or the demo-console button creates a real payment link/mandate — verified live this session: a real contact submitted for INV-002 (`"Ramesh Traders Real"`, `9876543210`) produced a genuine TEST-mode subscription (`sub_TUO8...`, real `short_url`) whose `customer_used`/`contact_source` fields in the API response confirm the real name/phone actually reached Razorpay.

**The phone-validation choice.** `engine/action/contacts.py`'s pattern is `^\+?[1-9]\d{7,14}$` after stripping spaces/hyphens — an optional leading `+`, no leading zero, 8-15 digits. Deliberately NOT a single-country (e.g. India-only 10-digit) format: this is a demo-console contact book for a hackathon submission, not a KYC form, and the operator may type a bare 10-digit number or a `+91`-prefixed one. Malformed input (too short, too long, letters, a bare `+`, empty) raises a typed `ContactError` the API turns into a 422 before anything is stored — pinned by `tests/test_contacts.py`'s parametrized valid/invalid-phone suites. An empty or whitespace-only name is refused the same way.

**The debtor-level contact-key decision.** `WorldRunner._contact_key(entity_id)` returns the invoice's `debtor_id` when `entity_id` is a known invoice, else the entity_id itself (a Scene-2 cart has no debtor record). This means a contact submitted against ONE invoice automatically applies to every sibling invoice the same debtor holds — reusing the exact per-debtor scoping precedent the touch cap already established (packet P8's `touches_by_debtor`), and for the identical reason: a debtor is one human, and a debtor cannot sensibly have two different phone numbers on file depending on which of their invoices an operator happened to be looking at when they typed one in. `POST /entities/{id}/contact`'s response names every sibling this affects (`also_applies_to`) so the dashboard can say so rather than let an operator believe they updated only the one invoice in front of them.

**Byte-identical fallback, verified rather than assumed.** `resolve_contact()`'s "nobody has submitted a contact yet" branch reproduces the exact old hard-coded values (`DEBTOR_BY_ID`-derived name, `DEMO_CUSTOMER_CONTACT`, `DEMO_CUSTOMER_EMAIL`) byte-for-byte — pinned by `tests/test_contacts.py::test_resolve_contact_is_byte_identical_to_the_old_hardcoded_fallback_when_nothing_submitted` — which is what makes the seeded 45-day run's numbers provably unmoved: re-measured this session at **₹23,31,496 / 23 KEPT / 27 HUMAN_HANDOFF / 12 DISPUTED, `bound_violations()` empty**, identical to the pre-P15 baseline, with two fresh runners still byte-identical to each other.

**Email stays synthetic, always — not an oversight.** The brief was explicit that only name+phone collection was in scope; `resolve_contact()`'s `email` field is `DEMO_CUSTOMER_EMAIL` unconditionally, whether the contact source is real or demo-fallback. No email-collection UI was built.

**`MANUAL_REMINDER_CHANNELS` grew a third member: `"message"`.** This is a ledger-layer change only — `"message"` was ALREADY in every hard-bound enumeration in `state_machine.py` (`OUTBOUND_KINDS`, `TouchKind`) since Day 5, because ordinary autonomous messages have always existed as a kind. No bound was touched. Pinned exactly the way P14 pinned `sms`: `tests/test_reminders.py::test_message_reaches_identical_verdicts_as_voice_and_sms_as_a_manual_channel` runs `check_bounds()` pairwise across all three manual channels over 1000 random inputs and asserts identical verdicts and reasons.

**Cost:** real UI/API surface area added (a new `Contact`/`ContactBook` module, three new API routes, a new dashboard panel), no design law changed, no bound touched, no existing behaviour altered when nothing is submitted. Full before/after test counts and the one real discrepancy from the pre-dispatch prediction (the honesty-text substring three P14 tests hard-coded, which needed updating once the wording legitimately grew a third channel) are in `tracking/BUILD_LOG.md` under the same date.

### 2026-08-26 — packet P14 as built: the judgment calls inside the reminder subsystem
Follow-up to the scope entry directly above, which records the *decision to build this*. This one records what the build actually decided. Same date, user-confirmed 2026-08-26 with the freeze risk accepted; the pre-agreed cut order is unchanged, except that item 4 ("TTS voice note") now means this whole subsystem rather than one static MP3.

**The real/simulated split, precisely.**

| | Real | Simulated |
|---|---|---|
| **Voice** | The audio. `gTTS` calls Google Translate's TTS endpoint and writes a genuine, playable MP3 to `demo_assets/voice_notes/<entity>-<action>.mp3`. Verified live 2026-08-26 end-to-end through the API: 50,112-byte file, MPEG frame-sync header `ff f3`, served back as `audio/mpeg`. | The dial. No phone rings. No Twilio/Exotel/any telephony credential exists in this repo. Every record carries `dial_status: "simulated_no_telephony_provider"`. |
| **SMS** | The message text — a real string a human can read, quoting the ledger's own amount (or the operator's typed words). There is no generation step because the text *is* the content. | The send. No handset receives anything; no SMS-gateway credential exists. Every record carries `send_status: "simulated_no_sms_provider"`. |

The honesty fields are in the API payload (`GET /entities/{id}/reminders` returns an explicit `honesty` block) and on the dashboard panel, not only in code comments. Upgrade path stated in `engine/action/tts.py`: if real telephony/SMS credentials ever land, the generated MP3 becomes the media payload of a real call and `dial_status` starts reporting the provider's answer, with nothing above `_dispatch_voice` changing — the same way the Razorpay mandate rail flipped. **That integration was deliberately not built**: there are no credentials for it, and a stubbed provider fabricating delivery receipts would be worse than no provider at all.

**The call that actually mattered: `remind-now` is gated, and P13's demo console is not.** These two landed a day apart and look superficially alike — both are a human clicking a button — so the difference is settled once, here. `/create-mandate-now` (P13) deliberately skips `check_bounds()`: a person clicking once to watch a real Razorpay object get created is not the automated runaway the bounds were built to constrain, and it contacts no debtor. `/remind-now` is the opposite shape: it *sends a message to a debtor*, so it spends that debtor's real weekly touch budget and is refusable by exactly the bound an autonomous nudge is. `Ledger.manual_reminder()` runs `_gate()` at click time and returns `{"action", "blocked", "block_reason"}` — the same 200-with-a-refusal shape `approve_held` established in P9 (decision #7 there applies verbatim), so the dashboard reuses one "the guardrail said no" pattern instead of inventing a second. **A manual channel spendable for free would be a hole in bound #4, not a feature.** The debtor cannot tell whether the third message this week was decided by a ladder or by a merchant with a mouse; the bound protects the human being contacted, so it applies to both.

**No new bound constant, and none weakened.** `sms` was added to `OUTBOUND_KINDS`, `TouchKind`, `TOUCH_COUNTED_KINDS` and every bound enumeration `message`/`voice`/`link` already appeared in. Pinned by `test_reminders.py::test_sms_and_message_reach_identical_verdicts_on_every_input` — 2,000 random inputs asserting `check_bounds` returns the identical verdict *and* the identical reason for `sms` and `message`, plus the `check_bounds_detailed` lens invariant restated for the new kind. That test exists because "added to some enumerations and missed from one" is the precise shape of hole a new channel introduces, and hand-picked cases would not find it. Adding `sms` to `OUTBOUND_KINDS` also automatically strengthened the pre-existing parametrized bound tests and the 1000-walk fuzz in `test_state_machine.py`, which enumerate those sets rather than hardcoding kinds.

**Four smaller calls inside the same packet:**
1. **The autonomous trigger was upgraded, not invented.** `_ESCALATE_ACTION["ESCALATE_2"] == ("voice", {"stage": "firm"})` has existed since Day 5 and is untouched; it still reaches the wire via `_decide_action` → `_try_action` → `_gate`. P14 changed what a `voice` action *produces* (real audio instead of a text line on a "voice_note" rail), not when the agent decides to make one. Calls stay under the existing `voice` kind — no rename, no split. One cosmetic consequence: `VOICE_TEXT`'s literal `"[voice note, Hinglish] "` prefix was removed, because gTTS would have read the brackets out loud. It was a label standing in for audio that did not exist; the rail (`voice_note`) and the record's `channel` still say what the thing is, in the two places a machine reads rather than in the sentence a human hears.
2. **`stage` is fixed by the ledger, not accepted from the route.** `stage` is an input to `check_bounds()`, so a route that could pass `stage="legal"` would be a door onto legal communication the agent must never send (law 4). The operator picks the CHANNEL and may supply their own words; they do not pick the escalation stage. `custom_text` is content only — spoken/sent verbatim, never `.format()`ed (a human's sentence is not a template, and format() would let typed text interpolate system values into itself), never parsed for an amount or a date.
3. **Reminders are NOT registered as openable instruments, and P11 was left alone.** P11's 48h link-open window is about a LINK: it needs something openable and a signal it was opened. A voice note and an SMS carry no URL and produce no open event, so giving them a "never opened → soft refusal" verdict would manufacture a delivery signal that does not exist — exactly what P11 was careful not to do. They *do* still go through `sentinel.record_send_attempt(..., success=True, ...)` like every other dispatched instrument, so dead-letter/circuit-breaker bookkeeping stays consistent across kinds. No artificial retries were wired either: retries exist for something that can transiently fail, and dispatch contacts no provider that could. P11's `_mark_instruments_opened` was checked and is generic over whatever is in `_open_instruments`; it is untouched, and `test_reminders.py::test_reminders_are_not_registered_as_openable_instruments` pins the decision.
4. **TTS is opt-OUT (`PK_REAL_TTS=0`), the inverse of `PK_REAL_RAZORPAY`'s opt-in.** A Razorpay call moves against a real merchant account and costs something, so it must be asked for. gTTS is free and credential-less, and the whole point of the feature is that the audio is real — a demo defaulting to silent placeholders would be the dishonest option. A disabled run records `audio_generation: "disabled"`, deliberately distinct from `"failed"`: "we chose not to call" and "we called and it broke" are different facts and the record must not blur them. A genuine failure records `"failed"` plus the transcript and the error, and writes a sentinel audit entry — no network hiccup takes down a simulated day, and no failure is silent.

**Cost, measured rather than predicted: zero to the recovery numbers.** The seeded 45-day run is unchanged at 23 KEPT / 27 HUMAN_HANDOFF / 12 DISPUTED and **₹23,31,496**, `bound_violations()` empty, two fresh runners still byte-identical. The reason it is exactly zero is the most interesting finding in the packet and is written up in BUILD_LOG under the same date: **the autonomous voice escalation is attempted 4 times in the seeded run and refused all 4 times by `max_touches_per_week`** — by the time an entity reaches ESCALATE_2 its debtor's weekly budget is already spent. So the new channel generates no audio at all on the 45-day autopilot, which is also why the test suite makes zero network calls without needing to be told to. The bound is genuinely load-bearing on this channel rather than decorative; the demo path for real audio is the operator's `remind-now` button (or an entity whose debtor still has budget). That is a real limitation of the feature as it stands, stated rather than hidden.

### 2026-08-26 — packet P11: what counts as "the debtor opened the link" in a text-only world
**The question the spec never had to answer.** Master doc §7.2 gives the Sentinel a link-open timer ("sent != delivered != opened") and `link_timed_out()` implements it correctly. It presumes a click event exists. In this simulation it does not — there is no pixel, no redirect, no webhook. So the runner had `track_link_sent` and no way to ever say "opened", which is why every instrument soft-refused itself at 48h (packet P10's finding, BUILD_LOG 2026-08-26).

**Decision: any inbound message from the debtor marks every instrument still inside its window as opened.** Not "a reply that agrees", not "a reply whose extraction is L1–L3", not "a `confirm_mandate` move" — *any* message. Three reasons, in order of weight:
1. **It is the closest true statement available.** A human who types a reply into a thread whose last message carried a payment link has received and read that message. That is precisely, and only, what "opened" claims. Anything narrower would be inferring intent from a delivery signal.
2. **Agreement is already decided one layer up, and better.** Whether the debtor said yes is answered by the real extraction and the frozen persona move, feeding `ledger.process_event`. If the Sentinel also got a vote on it, a delivery-layer heuristic could contradict a judgment-layer decision — the inversion CLAUDE.md law 1 exists to prevent, just with a rules engine instead of an LLM.
3. **It is the version that cannot rot.** Taking the signal in `_inbound` — the one funnel every debtor message passes through — means a persona branch added later cannot forget to report engagement. A per-branch rule ("mark it in the `confirm_mandate` case") is the same shape of bug as the one being fixed.

**What still times out, deliberately:** `decide_reply_move` → `silence` and `decide_mandate_move` → `ignore` send no message at all, so nothing marks their instrument and the 48h window closes as a soft refusal exactly as before. That is the correct reading of both moves — "ignore" in the mandate table means the debtor did not answer the offer, not that they answered it dismissively. Pinned by `tests/test_integration.py::test_true_silence_still_soft_refuses_after_48h` against the run's own instance (INV-003, day 21 offer → `ignore` → day 23 soft refusal).

**Two smaller calls inside the same fix:**
- **The runner keeps its own index of outstanding instruments (`_open_instruments`) rather than reading the Sentinel's `link_sent_at` / `link_opened` sets.** The Sentinel stays the single source of truth about what happened to a link; this dict only answers "which windows are still open for this entity", which is scheduling state the runner already owns (it is the same object that schedules the `link_timeout` beat). Nothing in `engine/action/sentinel.py` changed — its public API was already correct, it was simply never called.
- **The window closes at the scheduled timeout beat whichever way it went.** `_resolve_link_timeout` drops the instrument from the index before evaluating, so a reply arriving a week later cannot retro-cancel a timeout that already fired and already moved state. Within a single virtual day, scheduled resolutions run before new beats (`_run_day`), so a reply on the same day-index as an expiry does not save it — day-granular timestamps cannot separate them, and "the window had already closed when the day began" is the reading that keeps `link_timed_out()`'s 48h meaning intact.

**Cost, stated plainly and measured, not predicted:** none to the recovery number — the 45-day run is **unchanged** at 21 KEPT / 27 HUMAN_HANDOFF / 3 DISPUTED and **₹23,31,496 (33.4%)**. What changed is the audit trail: 13 → **4** `mandate_refused` events, 10 → **4** entities barred from a future mandate offer, 13 → **4** soft-refusal entries. The full before/after table and the three-part explanation of why the money did not move (including one part of P10's diagnosis that measurement disproved — `trust.update_refusal` is pending-neutral, so no posterior moved) is in BUILD_LOG.md under the same date.

### 2026-08-26 — packet P9: the ten judgment calls inside the confidence gates + review queue
Master doc §2.3 states three gates in three lines and §3.6 states the queue in one; neither says how they compose with the bounds. Every call below is a decision the spec left open, made once, tested, and stated here rather than buried.

1. **The gate constants live in `ledger.py`, NOT in `state_machine.py`.** CLAUDE.md law 4 says "all bounds live as constants at the top of `state_machine.py`" — and these are not bounds. The bounds answer "is this action allowed?" and are absolute; the gates answer "do we trust what we READ enough to act unsupervised?", which is a property of the LLM boundary. Crucially the gates are strictly *weaker* than the bounds: they can only DEFER to a human, never permit. Nothing in `state_machine.py`'s bounds block was touched, and `check_bounds()` is unchanged.
2. **An extraction that carries no `confidence` at all is NOT gated.** The gate compares a number, and "we were told nothing" is not evidence of low confidence. Every producer inside the system supplies one (the runner writes it from the real `Extraction`); the ungated case is manual injection through `POST /events` in tests and demos. Pinned by `test_an_extraction_that_states_no_confidence_is_not_gated` so it stays a decision rather than becoming a surprise. A stale confidence is also cleared rather than carried forward.
3. **The money gate is scoped to the MANDATED branch only** — the one branch an *extraction* drives straight into money movement, which is exactly what §2.3 bullet 3 says ("any extraction that would trigger a MONEY action"). `mandate_execute` at AT_RISK is the one allowed retry of a mandate the debtor already approved (driven by a webhook, not by a reading of a sentence); the LINKED `link` is the post-refusal fallback; Tier-0 reserve capture involves no perception at all. **Both** candidates *inside* the MANDATED branch are gated, though — the offer and the link it falls back to when a bound refuses the offer — so a low-confidence read cannot reach the wire through the fallback door.
4. **The second sub-0.75 extraction holds a `message`/`stage:"clarify"` item rather than inventing a new action kind.** §2.3 says "still ambiguous after clarify → route to human-review queue" without saying what the human is approving. Holding the clarify message keeps "ONE clarifying question" true *of the agent* — it asks once and never again on its own — while giving the human the one lever that actually helps (ask again, with their eyes on the thread). No new `ActionKind` was added.
5. **A clarifying question is touch-counted like any outreach.** An agent that could ask "just to confirm?" for free would have found a way around bound #4. Costs us a real touch on ambiguous threads; that is the correct price.
6. **Reject on a held `mandate_offer` emits the payment-link fallback, and the fallback is NOT re-held.** The packet spec words reject as "falls back to the link/ladder path the same way a bounds-block does", and a bounds-block at MANDATED tries the link. Re-holding that link would be an infinite hold loop with a human at the bottom of it — and the click that just happened *is* the human review the money gate exists to obtain. The fallback still passes `check_bounds()`.
7. **A blocked approval returns HTTP 200 with `{"blocked": true, "block_reason": ...}`, not a 4xx.** The request was valid and the system did exactly what it should; a bound refused the action. Making it an error would teach the dashboard to treat a working stopping rule as a failure. The screen renders it in the error tone anyway, because the merchant's click did not achieve what they wanted.
8. **The formal-notice draft refuses BOTH approve and reject (403); `mark-handled` is its only button.** "Reject" on a notice the agent was never going to send is a meaningless state, and a 403 on both is one fewer way to misread the law. Enforced in the ledger (`sendable=False`), not only in the UI.
9. **`human_resolution` does not move trust.** A merchant closing a handoff as recovered/written-off is bookkeeping about OUR process, not new evidence about how this debtor behaves. Inventing a Beta update from an admin click would put a number in the trust curve that no debtor action earned. Promise records *are* closed (recovered → kept, written_off → broken) so law 5's "no silent deaths" holds on the promise ledger too.
10. **The pause kill-switch outranks the Tier-0 reserve debit.** A merchant who paused a thread has said "move no money on this", and a reserve capture is money moving, however few touches it costs. Pause is enforced inside the ledger's `_gate()` (the same chokepoint as the bounds), so it stops the thread everywhere, not just in the runner's outreach loop.

**Terminal-state immutability and its one exception.** `human_resolution` is the only event that can move a terminal state, and only from HUMAN_HANDOFF/DISPUTED to KEPT/CLEAN_LOSS. It is contained by construction, not convention: nothing in `engine/` emits it (asserted over a full 45-day run), `POST /events` refuses it with a 400 pointing at the real route, and `Ledger.resolve_handoff()` additionally refuses any entity that is not currently an open handoff or dispute. **It is deliberately EXCLUDED from `test_state_machine.py`'s 1000-walk fuzz pool** — that pool models event streams the *pipeline can actually produce*, and this one is not among them. Excluding it is the stricter choice: including it would have weakened the immutability tests into "immune to everything except the event we just added", whereas excluding it keeps them at "immune to every event the pipeline can produce" and pins the exception separately from both ends (`test_human_resolution_is_the_one_event_that_moves_a_terminal_state`, plus the two containment tests named above).

**Cost, stated plainly:** the 45-day heuristic run recovers **₹23,31,496 (33.4% of active-invoice value)** with nobody clicking, down from **₹25,59,383 (36.6%)** before P9 — two mandate offers that used to go out unsupervised now sit in a queue. With a merchant actually working the queue it goes the other way: see BUILD_LOG 2026-08-26 (P9) for the measured ₹31,74,725 / 26 KEPT with three approved clicks.

### 2026-08-26 — data/generate.py: the L1–L5 extraction ladder definitions
**What:** BUILD.md/master doc reference "L1–L5" levels throughout (e.g. the Acme Traders example extracts `{level: L1, amount: 40000, date: Fri, cond: null}`) but never define what distinguishes L1 from L2 from L3 etc. — that's deferred to Day-4 prompt-writing. Since the Day 1–2 dataset needs concrete per-message labels now, I fixed a 5-level ladder in `data/generate.py`:
- L1 — firm + unconditional: explicit amount AND explicit date
- L2 — firm but partially specific: only one of {amount, date} explicit
- L3 — conditional OR structured/partial: can't be captured by one amount+date pair — either contingent on a stated external condition ("once my client pays me"), or a split/partial-payment offer ("half now, half in 2 weeks"); the `condition` field carries the qualifying detail either way

- L5 — no commitment: silence-equivalent, deflection, dispute, or refusal
**Why L3 covers two cases:** initially treated "conditional" and "partial-payment" as separate concerns while labeling the dataset, then caught during a self-review pass (BUILD.md's "judge mode" re-read) that a strict contingency-only L3 didn't fit the partial-payment thread (T-16) — broadened the definition rather than inventing a 6th level, since both cases share the same practical consequence: the state machine can't execute a single clean mandate from the message alone.

BUILD.md's own fallback path (documented in BUILD.md Day 4) is "merge L2/L4" if accuracy is low, which is coherent under this ladder (L2 and L4 are the two levels most likely to be confused: both lack full amount+date specificity, differing mainly in how resolvable the vague part is).

### 2026-08-26 — packet P10: how "show the guardrails" was made impossible to lie with
**What:** `engine/judgment/state_machine.py` gained `check_bounds_detailed()` (a list of `BoundsCheck(name, passed, detail)`) and `engine/judgment/ledger.py` gained `gate_log: list[GateRecord]` — the full per-bound checklist recorded at the instant `_gate()` reached its verdict. `check_bounds()` itself is byte-for-byte unchanged: same signature, same short-circuit, same single reason, same tests.
**Why a second function instead of rewriting the gate to return a list:** a gate should stop at the first refusal — that is what makes it cheap and what makes its reason unambiguous. What a *human* needs is the opposite: every check, including the ones a short-circuit never reached, and the numbers each compared. Those are two different jobs, so they are two functions, bound together by a proven invariant rather than by a shared implementation: `check_bounds(x).allowed == all(c.passed for c in check_bounds_detailed(x))`, asserted over 5000 random (entity, action_kind, params, touch-window) combinations, **plus** that the first failing check is the bound `check_bounds()` names in its reason (`tests/test_state_machine.py::test_check_bounds_detailed_can_never_disagree_with_check_bounds`). Without that test the screen could show a checklist the decision never reached, which is CLAUDE.md law 8 broken in the most convincing possible way — with a tick next to it.
**Why the checklist is RECORDED rather than recomputed:** explaining a day-3 decision by re-running the bounds against today's entity state would put numbers on screen that the system never decided from — the touch window especially, which moves every day. `_gate()` therefore writes a `GateRecord` (params, verdict, checklist, and the audit entry id it produced) next to the verdict, and the API attaches it to the exact audit entry it belongs to. Nothing reads a `GateRecord` to decide anything; it is append-only bookkeeping.
**The merchant kill-switch is in the recorded checklist but NOT in `check_bounds_detailed()`.** It is not a hard bound (it is a human's pause, enforced in the ledger ahead of the bounds), so it stays out of `state_machine.py` — but a recorded checklist that omitted it would show "all bounds passed" beside a refusal. `_gate()` prepends it, which keeps `allowed == all(checks passed)` true for a `GateRecord` exactly as the invariant keeps it true for the bounds alone.
**Cost:** one extra `check_bounds_detailed()` call per gate (~259 gates over a 45-day run) and a per-day snapshot of entity + trust state in `WorldRunner.day_snapshots`. No behaviour change anywhere; 394 pre-existing tests unchanged and green.

### 2026-08-27 — Step 6: RBI pre-/post-debit notices are deliberately exempt from MAX_TOUCHES_PER_WEEK
**What:** two new `ActionKind`s, `mandate_pre_debit_notice` (T-1 warning before a confirmed mandate executes) and `mandate_post_debit_notice` (confirmation after it executes successfully), close the "compliant escalation" pillar's last gap — RBI's E-Mandate Framework requires both, and neither existed before this packet (`tracking/TRACK_BAR.md` §2 had genuinely marked pre-debit as not yet built; the plan that scoped this work assumed it already existed, which turned out to be wrong — worth a note since it means the plan's own premise was corrected mid-step, not silently followed).
**The judgment call:** both kinds are deliberately absent from `state_machine.OUTBOUND_KINDS` and `ledger.TOUCH_COUNTED_KINDS`, so `check_bounds()`'s touch-cap, terminal-state and legal-stage checks do not apply to them, and a merchant's own `MAX_TOUCHES_PER_WEEK` budget cannot suppress them.
**Why this is not a hole in bound #4:** these are not discretionary outreach — they are mandatory disclosures about money the debtor already committed to (T-1) or that already moved (post-debit). A real bank does not skip a legally required debit notice because the merchant already contacted the customer twice that week for something else; making these two kinds compete for the same budget as a collections nudge would be the actual compliance bug. `check_bounds()` is still called on them via `Ledger._try_action()` (law 4 holds to the letter — nothing constructs an Action outside the gate), it simply has no applicable check for these two kinds by construction, which is why `check_bounds_detailed()` reports an empty checklist for them and `engine/integration/day_story.py`'s `_guardrail_summary()` was changed to render no panel at all for an empty checklist, rather than a misleading empty "all green" one.
**Real bug found while wiring the post-debit side:** the first version passed the ledger's returned `Action` from the `mandate_execute_success` event as the post-debit notice's transaction reference — but a first-attempt success usually lands the entity straight on the terminal state KEPT, which needs no further Action, so `ledger.process_event()` legitimately returns `None` even though the debit genuinely succeeded. The notice was silently skipped whenever that happened (caught by `tests/test_integration.py::test_a_confirmed_mandate_gets_a_pre_debit_and_a_post_debit_notice` against the real seeded run: `len(post) == 1` failed with `0`). Fixed by referencing the real `Event` id instead (`_emit()` always appends the Event before deciding whether a further Action is needed, so it is always there) — full story in `tracking/BUILD_LOG.md` 2026-08-27.
**Cost:** two pre-existing queue-side touch-cap tests (`test_touch_cap_holds_in_the_message_queue`, `test_touch_cap_is_enforced_per_debtor_not_just_per_invoice`) had to learn the same exclusion the implementation applies (`TOUCH_CAP_EXEMPT_KINDS`), or they would fail on messages that were never meant to be touch-capped in the first place — not a weakening, the same law re-stated correctly. `messages_sent` in the pinned 45-day distribution moved 100 → 111; every money, state-distribution and promise figure in that same test is unchanged, confirmed by a byte-for-byte diff of `eval/run_arms.py`'s Arm C output before and after this change.

### 2026-08-28 — a real mandate's debit date can never be the simulated invoice's own `due` field
**What:** the user's first genuine live IVR call surfaced a real Razorpay rejection (`"start_at cannot be lesser than the current time."`) — `invoice.due` was being used directly as a REAL mandate's `start_at`, but every invoice in this dataset is deliberately overdue (due in the past), so that field can never be a valid real-world future commitment date once actual money is involved. Full diagnosis in `tracking/BUILD_LOG.md`, 2026-08-28.
**The decision:** a real Razorpay `start_at`/`debit_date` defaults to real wall-clock `date.today() + 7 days` (`_real_future_debit_date()`, api/main.py) whenever no explicit date is supplied — never derived from the ledger's own `due` field for a REAL call. This is deliberately different from every OTHER place this project copies a value from the ledger (amounts, always — CLAUDE.md law 2): a debit DATE, unlike an amount, was already an explicit, human-overridable field in `create-mandate-now`'s own request body before this fix, so treating it as computed-with-a-sensible-default rather than ledger-sacred is consistent with existing precedent, not a new exception carved out for convenience.
**Why 7 days, not some other number:** it is not an arbitrary pick — it is the exact offset already verified live and accepted by Razorpay's real API during the P12 mandate-rail-pivot verification (`sub_TUM5ilVyr8rpZZ`, `start_at` 7 days out). Reusing a number that has already been proven to work beats inventing a new one.
**Cost:** `create-mandate-now`'s own long-standing default silently had the identical bug (never caught because every prior live verification of that route passed an explicit override) — fixed in the same pass rather than left as a known landmine, and its existing test (`tests/test_demo_console.py`) updated from asserting the buggy behavior to asserting the fix.

### 2026-08-28 — Auditor: a dedicated RNG stream, and quarantine as an additional hold reason, not a second gate
**Context:** with the live-call debugging settled, the next planned, already-scoped, currently-unbuilt piece of BUILD.md/master doc §7.3 was the Auditor — the last item before CLAUDE.md's own pre-agreed cut order (Reserve failover → Scene 2 → **Auditor** → TTS voice), and the only one of those four not yet built (Reserve failover and TTS voice were both already live; Scene 2 partially exists). Built rather than cut, since freeze is still several days out.

**Decision 1 — the Auditor's sampling RNG must never be `WorldRunner.rng`.** That shared stream drives every persona decision in strict sequence (reply moves, mandate moves, kept/broken promises, template choices) across the whole 45-day run. Interleaving Auditor sampling draws into it — even just calling `.random()` once per extraction to decide whether to sample — would shift every persona draw after the first sample, silently changing the pinned numbers (recovered amount, KEPT/HANDOFF/DISPUTED counts, `messages_sent`) purely as a side effect of turning a system-health feature on. `WorldRunner.__init__` instead constructs a SECOND, independently-seeded `random.Random(seed)` dedicated to the Auditor. Same seed value (still deterministic, still CLAUDE.md law 6), separate stream (zero interference). Verified directly rather than assumed: the full pre-existing pinned-number test suite (`test_the_45_day_distribution_is_the_number_the_docs_quote` and neighbors) stays green with the Auditor wired into every `WorldRunner`, and `tests/test_auditor.py` has a dedicated test asserting the two generators are different objects.
**Cost:** none — this is the same "isolated, restored-after" discipline already used for the mandate-acceptance sensitivity sweep (`eval/run_arms.py`'s `_scaled_mandate_table`) and the RBI notices' touch-cap exemption. A pattern this project keeps reaching for, not a one-off.

**Decision 2 — quarantine widens the hold check for NEW decisions; it does not retroactively release or re-hold anything already decided.** `Ledger._decide_money_action` now holds every money-adjacent action while `self.auditor_quarantined` is True, in addition to the existing single-extraction confidence gate — same queue, same `_hold_action` path, no new mechanism. Flipping quarantine off does not walk back through `held_actions` and release ones that were held while it was on; a merchant still has to click Approve on each, exactly like the ordinary confidence-gate holds (AI_JUDGMENT.md item 8: "There is deliberately no 'the extractor is more confident now, release it' path"). Quarantine inherits that rule rather than getting an exception, because a held item is a human's decision to make, not a flag's.
**Why this needed stating rather than assuming:** the first version of the "quarantine lifts, action goes through" test re-fired the identical event on the SAME entity and got `None` back — not because the fix was wrong, but because `Ledger.process_event()` short-circuits when nothing about the entity's state has changed, so the second call never even reached `_decide_money_action` to re-evaluate anything. Fixed by testing on a fresh entity/decision point instead of assuming a retry-in-place semantics this system was never built to have.

**What Auditor does NOT touch:** `state_machine.py`'s bounds are unchanged (CLAUDE.md law 4 — this is a NEW reason to hold, not a new bound, and it lives in the ledger's own decision logic exactly where the existing confidence gate does, not in `check_bounds()`). `config/agents.yaml`'s `auditor.*` section moved from "honest placeholder" to "actually wired" (`engine.config.build_auditor()`, mirroring `build_sentinel()`) — the shipped yaml still matches every builtin default exactly, so an untouched checkout behaves identically to before this packet, same acceptance bar packet P6 set for Sentinel's own wiring.
