## 2. Compliant escalation — 🟡 partial
- State machine stages: ✅ implemented, `engine/judgment/state_machine.py` (NEW→TRIAGED→ENGAGED→PROMISED→MANDATED/LINKED→AT_RISK→ESCALATE_1..4→terminal, DISPUTED reachable from anywhere)
- Merchant-review gate at legal/formal-notice stage: ✅ enforced — `check_bounds()` blocks any `message` action with `params.stage=="legal"`; `ledger.py`'s escalation handler routes that block to a `human_handoff` action instead of silently dropping it
- **Approval queue — ✅ REAL as of packet P9 (2026-08-26).** Master doc §3.6 asks for an approval queue "only for (a) low-confidence money actions and (b) formal-notice stage", plus a one-click thread pause. All three exist and act:
  - **(a) Low-confidence money actions.** Master doc §2.3's third gate is wired: an extraction under **0.90** that would trigger a money action produces a `HeldAction` (`ledger.held_actions`) instead of an Action on the wire — audited as `action held for human approval` BEFORE the queue is mutated, carrying `bounds_checked=False` because it has not passed the gate. **`check_bounds()` re-runs at APPROVE-CLICK time, not at hold time**, so a hold that went stale while the debtor's weekly budget was spent elsewhere is refused and audited rather than sent (`tests/test_ledger.py::test_approval_re_runs_check_bounds_at_click_time_not_at_hold_time`; it happens for real in a 45-day run — see BUILD_LOG 2026-08-26). Reject falls back down the ladder exactly the way a bounds-block does.
  - **(b) Formal-notice stage.** The ESCALATE_3 legal block still routes to `human_handoff`, and now ALSO puts the notice DRAFT in the queue with `sendable=False` — **no approve-send button exists anywhere in the stack for it**. `approve`/`reject` both return 403; the only button is "mark handled". The agent never sends legal communication, human click or not (CLAUDE.md law 4 / master doc §3.4). Proven end to end by `tests/test_review_queue.py::test_the_formal_notice_draft_can_never_be_sent_by_any_api_call` and `test_integration.py::test_the_formal_notice_draft_reaches_the_queue_and_never_the_wire` (no `stage=="legal"` action, no such message on any rail, over a full 45-day run).
  - **Clarify-first gate.** Under **0.75** the agent asks exactly ONE clarifying question (a real, bounds-checked, touch-counted `message` action) and never a second by itself — a second ambiguous read goes to the queue as "still ambiguous after clarification".
  - **Merchant kill-switch.** `POST /entities/{id}/pause` · `/unpause`, audited in both directions. A paused thread is skipped by the runner's outreach loop AND refused every outbound action inside the ledger's own gate — including the Tier-0 reserve debit. Measured against a control run: the paused invoice receives literally nothing across 45 days and still terminates (`test_integration.py::test_pausing_a_thread_stops_its_outreach_across_a_whole_run`).
  - **Closing a handoff.** `POST /entities/{id}/resolve-handoff {recovered|written_off}` → KEPT / CLEAN_LOSS via the `human_resolution` event — the ONE exception to terminal-state immutability, existing because a HUMAN is acting. Contained by construction: nothing in `engine/` emits it, `POST /events` refuses it (400), and the route refuses any entity that is not an open handoff/dispute. Terminal states stay immune to every other event, now asserted as 4 terminal states × the whole pipeline event vocabulary.
  - **In a 45-day heuristic run:** 4 items reach the queue — 3 money-gate holds (2 `mandate_offer`, 1 `link` at the MANDATED fallback, all at extraction confidence 0.78) and 1 formal-notice draft. 0 clarify messages, because the heuristic provider's confidence table bottoms out at 0.78 for the levels the runner books as promises; that is a property of one provider's numbers and is stated as such (the wire is proven by `test_integration.py::test_a_low_confidence_extraction_reaches_the_clarify_gate_in_the_real_pipeline`, which pushes a genuinely ambiguous read through the real runner).
  - Dashboard: `dashboard/src/screens/HumanReviewScreen.jsx` — three sections (held actions with Approve/Reject, open handoffs & disputes with Resolve recovered/written-off and the evidence-packet card, paused threads with Unpause), honest empty states, and a pre-click warning when an item's entity has already moved on.

## 3. Stopping rules — ✅ done
- Bounds constants (master doc §3.4), all 8, as named constants at the top of `engine/judgment/state_machine.py`: `MAX_TOUCHES_PER_WEEK`, `RENEGOTIATION_CAP`, `MANDATE_AMOUNT_CAP`, mandate-must-equal-ledger-amount (enforced in `check_bounds`, not a constant per se), `RETRY_ON_EXECUTION_FAILURE`, dispute-instant-stop (`TERMINAL_STATES` + `OUTBOUND_KINDS` gating), legal-stage-to-merchant, no-mandate-reoffer-after-refusal (`mandate_refused` flag)
- **Scope of the touch cap = PER DEBTOR**, as CLAUDE.md law 4 and master doc §3.4 word it ("max_touches_per_week = 2 (per debtor/customer)"): `check_bounds()` counts the rolling 7-day window across every entity the debtor holds, taking that window as an argument so the gate stays a pure predicate. Through packet P2 it was enforced per invoice, which let a debtor with five overdue invoices collect six messages a week; fixed in P8 (worst rolling per-debtor window over a 45-day run: 6 → 2, at a real and openly reported cost to the recovery number — see BUILD_QUALITY and BUILD_LOG). Every message the system sends is now Action-backed and touch-counted; there is no outbound copy that skipped the gate.
- pytest file that tries to violate each one: `tests/test_state_machine.py` — 8 dedicated bound-violation tests plus a per-debtor violation test and one violation test per touch kind (a link/mandate offer is a contact too, so the cap can't be dodged by switching instrument), plus the dispute-from-any-state (11 starting states × 2 test forms) and 1000-random-sequence termination tests (**171 tests** total across `test_state_machine.py`/`test_ledger.py`/`test_trust.py`, all green)
- **The bounds are now VISIBLE per decision, and provably so (packet P10).** `check_bounds_detailed()` sits beside `check_bounds()` in `state_machine.py` and reports every applicable bound with the real figures it compared ("touches in the last 7 days across this debtor's entities: 2/2 (limit 2)", "mandate amount: Rs.40,000 <= cap Rs.100,000"). `check_bounds()` itself is unchanged — same signature, same short-circuit, same tests. The two are welded together by a proof, not by convention: `tests/test_state_machine.py::test_check_bounds_detailed_can_never_disagree_with_check_bounds` asserts over 5000 random inputs that `allowed == all(checks passed)` **and** that the first failing check is the bound the refusal reason names, so the dashboard can never render a checklist the real decision didn't reach. `Ledger._gate()` records that checklist (`gate_log`) at the moment it decides, linked to the audit entry it produced — the Day Story screen shows the working the decision was actually made from, not a re-derivation against today's state.
- **The bounds survive the human, too (packet P9).** The new approve-click path does not get a private door: it re-enters the SAME `check_bounds()` at click time, so a human approving a stale hold is refused exactly like the ladder would be — and the merchant kill-switch is enforced at that same chokepoint rather than in the UI. `tests/test_ledger.py::test_approval_re_runs_check_bounds_at_click_time_not_at_hold_time` and `::test_approving_a_hold_on_an_entity_that_has_since_terminated_is_refused` are the two that would fail if that ever changed; `test_integration.py::test_no_action_is_ever_constructed_outside_the_ledger` checks the Action id sequence across emitted AND held actions is one gapless run, so no layer can mint an Action around the gate.
- **A new channel got no new allowance (packet P14, 2026-08-26).** The reminder subsystem added an `sms` outbound kind and upgraded `voice` to real generated audio. Neither got a bound of its own: `sms` was added to `OUTBOUND_KINDS` / `TouchKind` / `TOUCH_COUNTED_KINDS` and rides `MAX_TOUCHES_PER_WEEK` on identical terms, proven by `tests/test_reminders.py::test_sms_and_message_reach_identical_verdicts_on_every_input` (2,000 random inputs, same verdict *and* same reason as `message`, plus the `check_bounds_detailed` lens invariant restated for the new kind). The operator's manual "send a reminder now" button goes through the SAME `_gate()` at click time and can be refused — a manual channel spendable for free would have been a hole in bound #4, not a feature (`::test_manual_reminder_is_blocked_once_the_normal_flow_spent_the_budget` exhausts the budget through the ordinary ladder first, then asserts the click is refused and audited). The best evidence that this is load-bearing rather than decorative: in the seeded 45-day run the agent's OWN voice escalation is attempted 4 times and refused all 4 times by the touch cap, so the channel emits nothing at all on autopilot (BUILD_LOG, same date).
