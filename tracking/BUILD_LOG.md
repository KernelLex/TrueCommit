## Entries

### 2026-08-26 — pydantic field named `date` broke on Python 3.14
**What broke:** `engine/schemas.py` raised `TypeError: unsupported operand type(s) for |: 'NoneType' and 'NoneType'` on import, from `Extraction.date: date | None = None`.
**Root cause:** Python 3.14 ships PEP 649 (lazy annotation evaluation) as default — pydantic resolves each field's string annotation against the class's own namespace. Since the field is named `date` (matching BUILD.md §2's `Extraction {..., date: date|None, ...}` literally), by the time pydantic evaluates the annotation, the class-namespace name `date` is already the field's own default (`None`), not the imported `datetime.date` type — so `date | None` becomes `None | None`. This wasn't a `from __future__ import annotations` issue (removing it didn't fix it) — 3.14 does this regardless.
**Fix:** switched `engine/schemas.py` from `from datetime import date, datetime` to `import datetime as dt`, referencing `dt.date` / `dt.datetime` everywhere. A module-qualified reference can never collide with a same-named field.
**Design change:** none to the contracts themselves (field is still named `date` per spec) — just the import style in this one file. Worth remembering for any other pydantic model with a field name that shadows a stdlib type (e.g. a future `id`, `type`, `date`, `list` field).

### 2026-08-26 — sim/run.py emitted events that didn't match the Event schema
**What broke:** nothing crashed, but `sim/run.py`'s `EventLog.emit()` originally wrote a `day: int` field instead of the `ts: datetime` field BUILD.md §2's `Event` contract actually specifies — the simulator would have silently drifted from its own schema if I hadn't cross-checked by explicitly validating the output against `engine.schemas.Event`.
**Root cause:** wrote the simulator's internal day-counter straight into the output dict without mapping it back to the shared `Event` contract — easy to do since the simulator's own logic only ever needs `day`, not a timestamp.
**Fix:** `EventLog.emit()` now constructs a real `engine.schemas.Event` (computing `ts` from a `SIM_EPOCH` + day offset) and validates it before appending; `day` is kept alongside `ts` in the output dict purely as a dashboard-timeline convenience, not part of the contract.
**Design change:** confirms the value of validating generator/simulator output against the shared pydantic contracts as a standard last step, not just trusting that "it ran without an exception."

### 2026-08-26 — escalation stage could desync from state, breaking the ladder cap
**What broke:** `tests/test_state_machine.py::test_escalation_ladder_is_capped_and_forces_handoff` — an entity at `state="ESCALATE_4"` that received another `promise_broken` event went to `ESCALATE_1` instead of `HUMAN_HANDOFF`.
**Root cause:** `_escalate()` incremented `entity.escalate_stage` (a separately-tracked int counter) rather than reading the stage back out of `entity.state`. The test constructed an entity with `state="ESCALATE_4"` but left `escalate_stage` at its default (0), so the increment produced 1, not 5 — the two fields had silently drifted apart. In the real system `state` and `escalate_stage` always move together (only `_escalate()` sets either), so this specific desync can't happen via normal event processing — but the fact that the schema *allowed* constructing an inconsistent entity, and the ladder-cap logic silently trusted the wrong field, was the real bug.
**Fix:** `_escalate()` now derives the current stage from `entity.state` itself (via `ESCALATE_STATES.index(...)`) whenever `state` is already one of the `ESCALATE_*` values, falling back to `escalate_stage` only when starting fresh from a non-escalating state — so the cap holds even if the two fields are ever out of sync.
**Design change:** a reminder to prefer a single source of truth over two fields that are supposed to stay in lockstep by convention; caught here because the bounds tests construct entities directly at arbitrary states rather than only ever driving them through `transition()`.

### 2026-08-26 — the 90% triage gate is unreachable on 36 of the 60 invoices (dataset, not model)
**What broke:** the first offline triage measurement came in at **71.7%** against a ≥90% gate. BUILD.md Day 3's own instruction for that case is "below 90% = fix prompt, not model" — so I went looking for the prompt bug. There wasn't one.
**Root cause:** only 24 of the 60 invoices have a conversation thread. The other 36 are the procedurally-generated "filler" invoices from `data/generate.py`, and for those the ONLY inputs any provider gets are two booleans (`delivery_confirmed`, `payment_failed_attempt`) — which `flags_for_cause()` deliberately flips ~10% of the time — while their ground-truth cause was drawn from a persona-weighted distribution those two booleans cannot express. I computed the flag-only ceiling (always predict each `(delivery_confirmed, payment_failed_attempt)` group's most common label): **61.1%** on that group. The heuristic scores 58.3% there — within one invoice of the information-theoretic maximum. On the 24 invoices that actually have a thread it scores **91.7%**, i.e. it clears the gate wherever the gate is answerable. No prompt and no model can recover the other 15; the information is not in the input.
**Fix:** did NOT tune anything to close the gap — that would be fitting noise. Instead `eval/triage_eval.py` now reports the split (`with_thread` / `no_thread` / `no_thread_flag_only_ceiling`) alongside the headline number, so the honest reading travels with the metric. The headline stays 71.7% and stays a FAIL against the 90% gate.
**Design change:** the "measured vs simulated" table needs a third column — *measurable*. A gate is only meaningful over inputs that carry the answer. Two follow-ups for the lead to choose between (neither done here, both touch `data/generate.py` which is out of this packet's scope): (a) give the filler invoices at least a stub thread so their labels become inferable, or (b) restrict the triage gate to the threaded subset and say so out loud. Option (b) costs nothing and is already computed.

### 2026-08-26 — the shared LLM prompts never state today's date; relative dates resolve against nothing
**What broke:** first real out-of-sample measurement (packet P5, qwen2.5 via Ollama) came in well under the heuristic baseline — extraction 77.3% (7b) / 59.1% (3b) vs the 85% gate — with date agreement the standout gap: 63.6% (7b) vs the heuristic's 93.2%. One live smoke call resolved "Friday" to **2023-10-06**.
**Root cause:** the prompt assembly (shared by the anthropic and ollama providers — same code path) sends the message text and thread but never a reference date. A model cannot resolve "by Friday" or "month end" without knowing when "now" is; the heuristic provider never had this problem because it reads `message.ts` directly. This is an input bug in our assembly, not a model-capability finding — it was invisible until a real LLM ran, because the heuristic doesn't use the prompts and the anthropic provider has never had a key to run with.
**Fix:** dispatched as its own packet (prompt iteration per BUILD.md Day 4's sanctioned loop): inject "Today is {message date} ({weekday})" into the LLM user content, note in extract.md that dates resolve relative to that line, re-measure. Secondary confusions logged for the same packet: 3b over-predicts L5 on vague acknowledgments (precision 0.37), L2 is the weakest level for both models.
**Design change:** perception eval numbers are now three-way honest: heuristic (in-sample), local LLMs (out-of-sample), and the gap between them is diagnostic signal, not embarrassment — this entry exists because measuring before tuning caught a bug that reading the prompts five times had not.
**FIXED 2026-08-26 (packet P7) — see the follow-up entry below for what it measured.**

### 2026-08-26 — reference-date fix landed; extraction clears the 85% gate on a local 7B
**Follow-up to the entry above.** Two changes, and they are two DIFFERENT kinds of change — the distinction matters more than the number:

**(1) The objective input bug.** The duplicated inline user-content assembly in `providers/ollama.py` and `providers/anthropic_provider.py` was deleted and replaced by one shared `engine/perception/assembly.py`. Extraction calls now open with `Today is 2026-08-26 (Wednesday).` derived from `message.ts` (never the wall clock — CLAUDE.md law 6), every thread line carries its own date, and the prompt says dates must come back as ISO. Triage gets the same treatment (issued/due dates, days past due, and a "Today" line derived from the latest message on record; an invoice with NO thread is told so explicitly instead of having a date invented for it). Two copies of an input bug was one copy too many — that is why the fix is a shared module and not a patch in each provider.

**(2) Label-aware prompt tuning, disclosed as such.** `prompts/extract.md` was restructured around an explicit decision order (L5 → L3 → fields decide L1/L2 → L4) and gained five few-shots plus three contrast rules, each traceable to a specific miss in `metrics/extraction_accuracy_ollama_7b.json`. These are in-distribution improvements written while looking at which of the 44 labelled messages the model got wrong. They are legitimate under BUILD.md Day 4's own loop ("iterate prompt — more few-shots for confused pair, tighten definitions"), but they are NOT the same evidence as (1): the reference date was objectively missing, whereas these teach the ladder's existing semantics better. Every rule added is general (a field-consistency rule for L1/L2, a gating-verb rule for L3, a bare-acknowledgment rule for L5), not a memorised message.

**Measured (qwen2.5:7b, same 44 hand labels, out-of-sample):**

| | before | after |
|---|---|---|
| overall level accuracy | 77.3% (FAIL) | **88.6% (PASS, gate 85%)** |
| date agreement | 63.6% | 70.5% |
| amount agreement | 86.4% | 93.2% |
| L1 P/R | 0.89 / 0.73 | 0.85 / 1.00 |
| L2 P/R | 0.50 / 0.60 | 1.00 / 0.40 |
| L3 P/R | 0.80 / 0.80 | 1.00 / 0.80 |
| L4 P/R | 0.87 / 0.81 | 0.84 / 1.00 |
| L5 P/R | 0.67 / 0.86 | 1.00 / 0.86 |

The ladder stays at five levels — BUILD.md's L2/L4 merge fallback was NOT taken and is not needed.

**What did NOT work, kept here because it is the honest half.** The same treatment applied to `prompts/triage.md` (teaching the DECISIONS.md-pinned rule that `non_responsive` requires outreach that went unanswered) moved the all-60 headline 53.3% → 65.0% and the no-thread group 27.8% → 52.8%, but cost the **gated** metric: the 24 threaded invoices fell 91.7% → 83.3%, because a 7B given a "no outreach yet → cashflow_delay" rule starts answering `cashflow_delay` for threads that DO have unanswered outreach (INV-021, INV-026). Three wordings were tried (prose rules, a decision table, a numbered stop-at-first-match list); all three landed at 83.3% threaded. **`triage.md` was therefore reverted to its pre-P7 wording** — trading a gated metric for an ungated one whose ceiling is a proven 61.1% would be metric-shopping, not improvement. Triage numbers are consequently unchanged from the P5 baseline (53.3% overall, **91.7% threaded**), which also proves the assembly change alone had no measurable triage effect. The measured trade-off is on the record for the lead if they ever want the headline instead.

**Design change:** prompt text is now part of the cache fingerprint. `assembly.prompt_fingerprint()` hashes all three prompt files plus an `ASSEMBLY_VERSION`, and both LLM providers fold it into `identity()` (`"ollama:qwen2.5:7b:prompts@<hash>"`). Before this, editing a prompt did NOT invalidate `.cache/perception/`, so a re-measurement after a prompt edit could have silently re-served the old wording's answers — the exact failure mode that would have made this packet's numbers meaningless. It over-invalidates on purpose (a triage edit also drops cached extractions): recompute costs minutes, a stale gate number costs credibility.

### 2026-08-26 — the local GPU died mid-eval, and the "don't fall back on HTTP errors" rule paid off
**What broke:** a triage eval run died at invoice ~40 with `OllamaProviderError: Ollama /api/chat returned HTTP 500 for model 'qwen2.5:7b': {"error":"an error was encountered while running the model: CUDA error: an illegal memory access was encountered"}`. Ollama itself stayed up (`/api/version` answered) but had unloaded the model (`/api/ps` → `{"models":[]}`).
**Root cause:** the local GPU/driver, not our code. Nothing in the repo can fix it; the run just has to be repeated.
**Why it is logged anyway:** this is the first real-world test of a design decision `providers/ollama.py` made on paper — connectivity failures (`httpx.TransportError`) degrade silently to the heuristic, but an HTTP error status raises a loud typed error instead. Had the 500 been treated as "Ollama is unavailable", the eval would have quietly finished with ~20 heuristic answers mixed into a file labelled `metrics/triage_accuracy_ollama.json`, and the number would have been a lie that nothing in the pipeline could have caught. It crashed instead. The rerun (cache made it cheap — completed invoices were already stored) produced a clean number.
**Also found, and it changes how these numbers must be quoted:** the same prompt + same model + `temperature: 0` is NOT byte-reproducible across runs on this stack. Three 7b extraction runs against the identical final tree scored 90.9%, 88.6%, 88.6% — a one-message swing (M-16-4 "sending now" flips between L1 and L2). So a local-LLM accuracy figure here carries roughly ±1 message (±2.3pp) of run-to-run noise and the honest way to quote it is "88.6%, gate cleared in all three runs", not a single decimal-precise number. The heuristic provider has no such problem (pure Python, byte-identical every time), which is exactly why CLAUDE.md law 6 keeps the deterministic provider as the default for seeded runs.

### 2026-08-26 — prompt few-shot and dataset label disagree about the same sentence
**What broke:** while writing the rules provider I hit a direct contradiction between two files that are both supposed to be authoritative. `engine/perception/prompts/triage.md` few-shot #3 labels *"the upholstery set arrived with 3 damaged panels"* → `delivery_dispute`. `data/generate.py` gives that same thread (T-12 / INV-031) the ground-truth cause `dispute`. An LLM following the prompt exactly would be marked WRONG by the eval.
**Root cause:** the prompt and the dataset were written in separate passes against a taxonomy (`InvoiceCauseType`) whose `dispute` vs `delivery_dispute` boundary was never pinned down beyond "depending on scope".
**Fix (in this packet, rules-side only):** pinned the boundary explicitly and documented it in `HeuristicParams` — **scope decides**. A debtor contesting the invoice or their obligation to pay it at all ("we're not paying this") is `dispute`, even when a delivery complaint is the stated reason; a complaint confined to the condition of what arrived, with no refusal to pay, is `delivery_dispute`. That reading matches both the schema docstrings and the prompt's own "depending on scope" line, and it reproduces the dataset labels for T-12, T-13 and T-14.
**Not fixed:** `prompts/triage.md` few-shot #3 still teaches the other reading, and prompts/data are outside this packet's write scope. **Flagged for the lead:** either amend that few-shot to include the refusal-scope rule, or relabel INV-031 — but they cannot both stand, or the Anthropic provider will be scored down for obeying its own prompt.

### 2026-08-26 — the "max 2 touches/week per debtor" bound is enforced per INVOICE, not per debtor
**What broke:** nothing failed — this only became visible once a full 45-day world ran end to end and I measured the message queue from the output side. Per invoice, the worst rolling 7-day window is **2** (the bound holds exactly). Per **debtor**, the worst window is **6**.
**Root cause:** CLAUDE.md law 4 and master doc §3.4 word the bound as "max 2 touches/week per debtor". `state_machine.check_bounds()` enforces it against `entity.touches`, and an entity is one invoice. Each of the 12 debtors holds five invoices, and each invoice runs its own independent ladder — so a debtor with three simultaneously-escalating invoices can legitimately collect three separate bounds-checked messages in the same week without any bound firing. Every individual action really did pass the gate; the gate is just scoped one level below where the law is written.
**Fix:** none applied. `engine/judgment/` is read-only for this packet, and quietly suppressing actions in the runner would hide the gap rather than close it (and would change recovery numbers for a reason no code comment could justify). Instead the behaviour is **pinned by a test that asserts the truth in both directions** — `test_touch_cap_is_enforced_per_invoice_not_per_debtor` asserts per-invoice <= 2 *and* asserts per-debtor > 2 — so the day someone fixes it, that test fails and forces the claim in CLAUDE.md/README to be updated at the same time.
**Design change:** flagged for the lead as a judgment-layer decision, not a runner one. Closing it means giving `check_bounds()` a debtor-scoped touch window (the ledger already has `debtor_of`), and accepting that a debtor with five overdue invoices then gets contacted about at most two of them per week — which is arguably the *correct* product behaviour and a better story ("we throttle the human, not the invoice"), but it is a real behaviour change to the recovery numbers and belongs to whoever owns the metrics.

**RESOLVED 2026-08-26 (packet P8, lead ruling).** `check_bounds()` gained a `debtor_touches: list[datetime] | None` argument and counts the 7-day window across it; the Ledger keeps `touches_by_debtor` and hands the right list in, so the gate stays a pure predicate with no hidden state reads (asserted by `test_check_bounds_stays_a_pure_predicate`). `EntityState.touches` still exists per-entity — the funnel, the timeline and the Tier-0 "0 touches" claim read it — but it is no longer what the cap is measured against. Carts scope by `customer_id`, which came free: the runner already registers a cart as a ledger record whose `debtor_id` is the customer. Omitting the argument treats the entity as its own debtor, which is the correct degenerate case and never more permissive than the old behaviour. The old truth-pinning test did exactly its job: it failed the moment the fix landed (`assert 2 > 2`) and is now `test_touch_cap_is_enforced_per_debtor_not_just_per_invoice`, asserting the law from the message queue rather than from the ledger's own counter so a leaking gate would still be caught. Worst rolling per-debtor window over a 45-day run: **6 → 2**. The price, paid openly and not tuned back: 29 KEPT → **23 KEPT**, 19 → **25 HUMAN_HANDOFF**, 3 DISPUTED unchanged; ₹40,62,231 → **₹25,59,383** recovered (58.2% → **36.6%** of active-invoice value). 149 touches were blocked and audited over the run — that is the bound working, not messages going missing. The compliant number is the number.

**Second-order effect worth stating** (found by measuring, not predicted): with the cap per debtor, a debtor's whole weekly budget can be spent on ONE invoice — the gentle nudge plus the mandate offer it earns — so a sibling invoice's *instrument* (15 `link` + 9 `mandate_offer` blocks) can now be blocked by a low-value nudge that arrived first. Invoices are worked in ID order, which is deterministic but not smart. Prioritising the touch budget (highest-value or highest-trust invoice first, instruments before nudges) is a real product improvement and would likely recover much of the 21.6-point drop — deliberately NOT done here, because choosing an ordering that raises the recovery number is exactly the tuning this packet was told not to do. Flagged for the lead as its own scoped decision. Related: no entity reaches ESCALATE_2 in the 45-day run any more, so the voice-note rung and the ESCALATE_3 legal/merchant-review block are no longer exercised by that run (both still covered by unit tests).

### 2026-08-26 — the ledger emits no Action for a plain nudge, so the runner sends none
**What broke:** not a crash — a design collision found while wiring the outreach cadence. BUILD.md's touch schedule is time-based (day 0/7/14/21/30, gentle→firm→formal), but `Ledger._decide_action` only returns an `Action` for `MANDATED` / `LINKED` / `AT_RISK` / `ESCALATE_1..4` / `DISPUTED`. An `outreach_sent` event against an `ENGAGED` entity changes no state, so `process_event` returns `None` — there is no Action for the gentle nudge, and therefore nothing that could legally be handed to the Messenger.
**Root cause:** two different mental models of "a touch". The ledger's model is instrument-or-escalation driven (something is offered, or the ladder climbs); the simulator's model is calendar-driven. Both are defensible; they just don't produce the same object.
**Fix:** the runner obeys the ledger rather than routing around it. It emits the `outreach_sent` event (which the ledger audits) and queues **no** message when no Action comes back. The alternative — drafting a nudge in the runner and pushing it to the Messenger — would be an outbound touch that never passed `check_bounds()`, i.e. exactly the untracked contact bound #4 exists to prevent. Consequence: every message in the queue is backed by a bounds-checked Action, which is what makes `test_touch_cap_holds_in_the_message_queue` a real proof instead of a tautology.
**Design change:** if the demo wants visible gentle-stage copy on screen, the right fix is in the judgment layer — give `ENGAGED` (and `TRIAGED`) a `message` / `stage="gentle"` entry in the ledger's action table, so the nudge passes the same gate as everything else. Logged rather than patched, because inventing an Action in the integration layer is the precise thing the design laws forbid.

**RESOLVED 2026-08-26 (packet P8, lead ruling)** — and fixed exactly where the entry said it belonged. `ledger.py` gained `_OUTREACH_ACTION`, a second action table mapping a ladder position to the message that beat justifies: TRIAGED/ENGAGED → `message` stage `gentle`, ESCALATE_1/2 → `message` stage `firm`. ESCALATE_3/4 are deliberately absent (stage 3 is the formal notice that law 4 sends to the *merchant* for review; stage 4 is a handoff) — so there is still a state where outreach yields no Action, but now that silence is a stated policy in a table rather than a hole. A second change was needed to make it reachable: `process_event` used to return None whenever the state didn't move, which meant an `outreach_sent` against an already-ENGAGED or already-escalating entity produced nothing at all. `outreach_sent` is now the one event that re-decides on a no-op transition, because a scheduled touch is a real request for contact even when the ladder doesn't climb. Every message the runner queues is now Action-backed, audited-before-sent and touch-counted — 90 of the 104 messages in a 45-day run are these, where before there were 12. The runner's side of it stayed small: one `gentle` copy template, and `_outreach` now returns early when the ledger hands back no Action, because simulating a debtor's reply to a message that was never sent would be worse than sending nothing. Pinned by `test_a_gentle_nudge_is_a_real_bounds_checked_action`, `test_outreach_at_an_escalation_stage_is_a_firm_message` and `test_no_agent_nudge_at_the_merchant_review_and_handoff_rungs`.

### 2026-08-26 — `VirtualClock.advance()` silently drops everything scheduled on day 0
**What broke:** found while reading `sim/clock.py` to reuse its cadence. `advance(n)` does `self.day += 1` *before* firing that day's callbacks, so a clock starting at day 0 never fires day-0 work. In `sim/run.py` that means `TOUCH_SCHEDULE`'s `(0, "gentle")` beat has never actually run: the standalone simulator's first outreach is day 7, not day 0. Confirmed directly — `sim.run.run(45, 42)` produces **zero** `outreach_sent` events on day 0, and day 0 contains only the 12 `cart_abandoned` events (which are emitted directly, not scheduled).
**Root cause:** off-by-one between "advance to the next day, then fire it" and "fire today, then advance". Invisible because the simulator's acceptance criterion is *determinism*, not coverage — a run that silently skips its first beat replays byte-identically every time, so the existing green test could never catch it.
**Fix:** none in `sim/`. The integration runner does **not** use `VirtualClock`; it runs its own day loop that simulates day-index 0 first (`advance(1)` => day 0 simulated, `day == 1`), so triage and the first gentle touch both land on day 0 as BUILD.md intends. Deliberately left `sim/run.py` alone: changing it would alter the 408-event output that BUILD_QUALITY's Day 1–2 acceptance row already records as verified, and that is a lead-level call, not a side effect of this packet.
**Design change:** "it replays identically" is a weaker guarantee than it feels like. Determinism tests prove reproducibility, never coverage — the simulator needed a second, independent assertion about *what* it fires, not just that it fires the same thing twice. The integration runner's tests are written that way on purpose (they assert states reached, money moved, levels extracted, rails used — not just that two runs match).

**RESOLVED 2026-08-26 (packet P8, lead ruling).** `VirtualClock.advance()` now fires today's callbacks and *then* moves on, instead of moving on and then firing. From `start_day=0`, `advance(45)` fires days 0..44 and leaves `day == 45` — which is also, deliberately, the exact convention `WorldRunner.advance` already used, so the repo's two clocks now mean the same thing by the same words. `sim/run.py` itself was not touched; its `(0, "gentle")` beat simply runs for the first time. **The recorded 408-event output changed to 463** (`outreach_sent` 126 → 158, `promise_made` 38 → 51). That number was never the invariant — determinism is — and it still holds: two fresh `python -m sim.run --days 45 --seed 42` runs produce byte-identical files (sha256 `e849ecc5…`, `diff` empty). ### 2026-08-26 — packet P6 (config/agents.yaml): two small design snags, both caught by the tests written for them
**What broke (1):** `AgentsConfig.model_validate()` raised `judgment: Input should be a valid dictionary` the first time `config/agents.yaml` was loaded, even though the file has a `judgment:` key.
**Root cause:** a YAML mapping key followed only by comment lines and no indented content parses to `null`, not `{}` — `judgment:\n  # comment\n  # comment\n` is `{"judgment": None}`, and `JudgmentSection` (which forbids extra keys, per law 4) doesn't accept `None`.
**Fix:** wrote `judgment: {}` explicitly on the key's own line, comments trailing after it. Cheap, and it made the "this section is deliberately, structurally empty" point more literally in the file itself.
**What broke (2):** a test asserting `engine/perception/cache.py`'s `enabled()` honors a tmp-path yaml failed — `cache.enabled()` kept returning the *real* `config/agents.yaml`'s value, not the test's.
**Root cause:** `engine.config.load_config()` is memoised by resolved path; the test called `load_config(tmp_yaml_path, ...)` (a specific path) to prime the cache, but `cache.enabled()` calls the loader with **no path**, which resolves to `DEFAULT_CONFIG_PATH` — a different cache key, so it silently reloaded the real shipped file instead of erroring.
**Fix:** the test now monkeypatches `engine.config.DEFAULT_CONFIG_PATH` itself before calling `load_config(force_reload=True)` with no path, so it exercises the exact call `cache.enabled()` makes rather than a different one that happens to look similar.
**Design note:** neither was a behaviour bug in the shipped app (both were caught before any commit-worthy state), but the second one is a reminder that a path-keyed memo cache needs its tests to go through the *same* resolution the real call site uses, not just "a config with the right value in it."

### 2026-08-26 — human mandate-approval test hit an account-level gate, not an API gate
**What broke:** the first real human-in-the-loop test of the mandate lifecycle — the user opened a genuinely-created eMandate registration short_url to authorize it as a real debtor would — died at Razorpay's hosted page with "No appropriate payment method found."
**Root cause:** diagnosed via `GET /v1/methods?key_id=...` (the same endpoint checkout.js uses): this fresh test account has **`upi: false` (UPI disabled account-wide) and `emandate` not enabled**. Registration-link *creation* succeeds regardless (the API issues the hosted invoice), which is why every earlier probe looked green — the gate only appears when a human actually tries to authorize, which is exactly the step nobody had performed until now. The user's question ("who is testing the approval?") found this.
**Fix/next step:** account-level enablement — UPI may be self-toggleable in the test dashboard (Account & Settings → Payment methods); eMandate/UPI-Autopay may need an activation request. The verification harness (`scripts/verify_mandate_lifecycle.py`: poll token → REAL recurring charge → REAL revoke) is built and waiting; the moment enablement lands, the full create→register→approve→execute→revoke chain completes for real in minutes. Until then execute/revoke stay `simulated:true` with this reason, and TRACK_BAR §0 says so.
**Design change:** none to code — but the real-vs-simulated table gains precision: "real in sandbox" must distinguish *API-real* (creation) from *flow-real* (a human can complete it), and only a human attempt reveals the second. Testing the happy path through the API alone would never have caught this.
